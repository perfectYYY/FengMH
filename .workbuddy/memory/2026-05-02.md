## boot_angle 与 IK 输出的 joint_pos 关系澄清

- 用户提问：传给 `go_set_position()` 的 `joint_pos` 是否应该减去 `boot_angle`？
- 结论：**不需要手动减**。`go_joint_pos_to_motor()` 公式中 `+ zero_offset` 已隐含该减法：
  - `motor_cmd = dir × joint_pos × gear_ratio + zero_offset`
  - 其中 `zero_offset = motor_raw - dir × boot_angle × gear_ratio`（校准阶段计算）
  - 展开后：`motor_cmd = motor_raw + dir × (joint_pos - boot_angle) × gear_ratio`
- 全链路：gait(足端位移 dx/dz) → leg_ik_solve_all(绝对关节角 theta) → try_set_pos(motor, theta) → go_set_position(pos=theta) → go_joint_pos_to_motor(zero_offset, pos) → 自动扣除 boot_angle
- 数值验证：FL_KNEE (dir=-1, boot_angle=-2.356, target=-2.0)，电机关节角变化恰好 = target - boot_angle = +0.356 rad ✓

## boot_angle vs zero_offset 概念澄清

- 用户纠正：boot_angle 和 zero_offset 不是同一个东西
- **boot_angle**：物理常量（配置表），上电时腿处于什么关节角度，在 IK 坐标系下
- **zero_offset**：运行时变量，校准阶段用 boot_angle + 当前电机位置反算出来，用于电机编码器空间↔关节角空间的平移
- 关系：zero_offset = motor_raw - dir × boot_angle × gear_ratio（go_enable line 276）
- 校准走查（关键三步）：
  1. 上电 zero_offset=0，读回 pos_rad → current_joint = dir × pos_rad / gear_ratio（相对值）
  2. raw_pos = go_joint_pos_to_motor(cfg, 0, current_joint) = pos_rad
  3. zero_offset = pos_rad - dir × boot_angle × gear_ratio（存运行时上下文，之后不变）
- 此后 joint_pos 直接传 IK 逆解值即可，不需要手动减 boot_angle

## 飞踢 Bug 修复：校准时序修正

### 问题根因
- `go_enable()` 的校准逻辑是死代码 — `task_chassis_init()` 不调用它
- `go_set_position()` 直接设 `mode=1`（闭环），不检查是否已校准
- 结果：上电 `zero_offset=0`，`cmd_pos = sign × joint_target × gear + 0`，完全偏离编码器当前位置 → 飞踢

### 修复方案（三处改动）

**1. 新增 `go_calibrate()` 函数**（`motor_go.c`）
- 从 `go_enable()` 中提取纯校准逻辑
- 只计算 `zero_offset = raw_pos - sign × boot_angle × gear`，不改变 `mode`
- `go_enable()` 改为调用 `go_calibrate()` + 设 `mode=1`

**2. `go_set_position()` 自动校准安全网**（`motor_go.c`）
- 首次进入闭环位置控制前，如果 `!calibrated && rx_cnt > 0`，自动调 `go_calibrate()`
- 即使 GO_ZERO 阶段没跑校准，首次设位置也能正确标定

**3. GO_ZERO 阶段主动校准**（`task_chassis.c`）
- 新增 `motor_go_calibrate_all()` 公开函数
- 在 GO_ZERO 阶段 `motor_go_send_all()` 之后调用 — 电机保持锁定态，仅更新 zero_offset
- 确保 GO_LEG_HOLD 切入闭环前，所有电机的 zero_offset 已就绪

### 修改文件清单
- `App/device/motor_go.h` — 添加 `motor_go_calibrate_all()` 声明
- `App/device/motor_go.c` — 新增 `go_calibrate()`，修改 `go_enable()`/`go_set_position()`
- `App/app/task_chassis.c` — GO_ZERO 阶段加入 `motor_go_calibrate_all()` 调用

## 机器人上电不站立的根因排查 (2026-05-02)

### 最初怀疑（已排除）：HAL UART 回调未连接
- 实际检查 `Core/Src/main.c:424-434` 发现 `HAL_UARTEx_RxEventCallback` 和 `HAL_UART_TxCpltCallback` 早就在 main.c 中通过 `extern` 桥接到 `bsp_uart.c`
- 回调一直完好，不是站不起来的根因
- 清理了 `stm32h7xx_it.c` 中误加的重复回调定义

### 真正根因：`motor_go_send_all()` TX busy 丢帧
- `motor_go_send_all()` 每条总线连续发 4 帧（4 个电机），每帧 ~17B
- `bsp_uart_send()` DMA 发送后设 `s_tx_busy=1`，后续发送被丢弃
- DMA TX 完成 ISR 虽会异步清 busy，但在同周期内来不及
- **实际效果**：每条 RS485 总线仅第 1 个电机收到指令（FL_HIP + RL_HIP），其余 6 个电机永远收不到

### 已修复: motor_go_send_all() 加 HAL_Delay(1)
- 参考 Desktop 版本 (`/Users/leon/Desktop/FengMH`) 的可工作发送逻辑
- Desktop 版本的 `MotorController_SendCommand()` 直接调用 `HAL_UART_Transmit_DMA()` + `HAL_Delay(1)`，没有 busy 标志检查
- **修复方案**：`motor_go_send_all()` 每次 `bsp_uart_send()` 后加 `HAL_Delay(1)`
  - 17B @ 4Mbps = ~42.5µs 物理传输，1ms = 23x 余量
  - DMA ISR 在延迟期间完成 → 清除 s_tx_busy → 下个电机正常发送
  - `#if !APP_TARGET_HOST` 保护，Host 编译不受影响
- **效果**：同周期内 4 个电机帧全部发出，不再丢帧
- FLASH: 71260B (6.80%), RAM_D1: 83160B (25.38%)

3. **多字节读 buffer 溢出修复**: acc_read_multi/gyro_read_multi 原用 uint8_t tx 单字节做 (1+len) 字节传输的 TX buffer，HAL_SPI_TransmitReceive 会越界读取栈内存。改为局部 tx[9] 数组
4. **预通信检查**: 复位前先读一次 CHIP_ID 确认 SPI 能通

**`Core/Src/spi.c`** — 删除 `SPI2_MspInit 1` USER CODE 块中的 VERY_HIGH pin speed 覆盖，恢复 CubeMX 默认 LOW speed (对齐 Wheel-legged)

## BMI088 硬件验证：Wheel-legged 参考固件烧录测试 (2026-05-02)

### 方法
- 用已知可工作的 Wheel-legged 参考固件烧录到同一块 STM32H723 板卡
- Wheel-legged 固件使用相同的 SPI2 引脚 (PC0=ACC_CS, PC1=MOSI, PC2=MISO, PC3=GYRO_CS, PB13=SCK)
- 如果 Wheel-legged 固件能读到 CHIP_ID → 硬件正常，问题在 FengMH 固件
- 如果也读不到 → 硬件故障

### 结果
- ✅ Wheel-legged ELF 烧录成功并验证 OK
- ✅ 固件正常运行 (FreeRTOS 调度中, PSP 活跃, 无 MemManage/HardFault)
- ❌ **BMI088 MISO 始终为 0x00** — 手动 OpenOCD SPI 操作：RXDR=0 连续 3 次

### 关键发现：gpio.c CS 初始电平错误

- 初始 CS=LOW 意味着 BMI088 上电就被选中 — 但这不会导致永久损坏

## 硬件烧毁事件 (2026-05-02)

### 现象
- BMI088 芯片烧毁
- STM32H723 主控芯片烧毁

### 固件隐患已修复
**`Core/Src/gpio.c:56`** — CS 初始电平 RESET → SET
- 原因: BMI088 CS 为 Active Low，初始 RESET(LOW) 意味着上电瞬间芯片就被选中
- 如果此时 SCK/MOSI 有噪声或初始化电平跳变，BMI088 可能误解释 SPI 命令导致内部状态异常
- 虽然通常不会直接烧毁芯片，但这是一个严重的设计缺陷
- 修复: `HAL_GPIO_WritePin(GPIOC, ACC_CS_Pin|GYR0_CS_Pin, GPIO_PIN_SET)`

### 待排查（硬件层面）
- 供电是否稳定（3.3V 稳压器输出是否有尖峰）
- 是否有引脚短路（用万用表测各引脚对地电阻）
- 上电时序是否有问题（VDD 和 VDDIO 是否同时上电）
- 静电/焊接问题

### 经验教训
- BMI088 CS 引脚必须初始为高电平（芯片未选中状态）
- 所有 Active Low 的片选信号都应该初始为高
- 上电前应先检查供电和引脚连通性
